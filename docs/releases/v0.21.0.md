## 拾穗 · Glean v0.21.0 — 数据地基

这一版不加新玩法，给以后的「手机电脑同步」打地基：每件穗、每根新枝、每条套路都有了一个全局唯一的身份证（uid），删除不再是真删而是先进回收站，备份换成了不怕大库的 .glean 格式，导入能认出重复、先告诉你会发生什么再动手。

**下载**：安卓 `Glean_0.21.0_android.apk` · Windows `Glean_0.21.0_x64-setup.exe`（或 `.msi`）

**升级**：直接覆盖安装。第一次打开会把数据库从 v7 升到 v8：只给每一行补 uid / 设备 / 修改时间，不删不改任何内容（v1–v7 每个历史版本都有回归测试，见下）。

**做了哪些（编号见 docs/ideas/ideas.csv）**
- **0601 全局 uid**：每件穗 / 新枝 / 套路一个 ULID（26 位，按时间排序），唯一索引。新写入自动盖上；旧数据升级时补上（uid 的时间部分就是它的记录时间）。备份、导入去重、Obsidian 的 `glean_id` 都改认 uid（本机编号挪到 `glean_n`）
- **updatedAt + deviceId**（0602 的前半）：首次启动生成本机设备 id（存本机，库里 meta 表留一份）；改了内容才更新修改时间和设备（打开详情、补缩略图、嫁接次数这些不算「修改」）。0602 的混合逻辑时钟（HLC）留给同步那一版
- **0603 删除改墓碑 + 0623 回收站**：删穗 / 删新枝只打上 `deletedAt`，从穗仓、搜索、嫁接、每日一穗、口味、导出里消失；原图、来源、嫁接次数都留着。设置 → **回收站 (n)**：一件件恢复 / 彻底删除、全部恢复、清空回收站；删除时的「撤销」也照旧。**30 天后自动彻底删除**（启动后空闲时清）
- **0607 流式备份 + 0608 .glean 格式**：备份是一个 ZIP（扩展名 .glean）：`manifest.json`（格式版本、导出时间、设备、条数、每个文件的 sha256 和字节数）+ `data.jsonl`（一行一条）+ `images/<sha256>.jpg`（原图原样二进制，按内容哈希命名，同一张图只存一份）。导出时一张一张读原图、边算哈希边写；安卓分块交给系统分享 /「下载」，Windows 用保存对话框逐块写盘。不再把整库拼成一个 JSON 字符串、也不再把图片转成 base64（原来 100MB 图要变成 136MB 字符串）
- **0611 导入按 uid 去重**：同一份备份导两次一条都不会多。旧备份没有 uid 的，按「记录时间 + 类型 + 标题 + 内容哈希」认重复
- **0610 三种导入方式 + 先预览**：选好文件先出一块预览——这份备份有几穗几新枝几张图，以及三种方式各会怎样：
  - **合并**（默认）：新的加进来，两边都有的以较新的那份为准
  - **只补缺**：只加本机没有的，已有的一件不动
  - **替换**：同一件以备份为准，本机不在备份里的**移进回收站**（30 天内可恢复，这就是替换前的本机快照），会再确认一次
  - 坏一张图只丢那一张（sha256 对不上就跳过并提示），`data.jsonl` 坏一行只丢那一行
- **旧 .json 备份照样能导入**（v0.1–v0.20 导出的、v0.20 兜底页导出的原始数据都行），同样走预览和去重
- **0710 Dexie 迁移回归套件**：`src/__tests__/fixtures/dexie/v1.json … v7.json` 是每个历史版本当年的表结构 + 当年形状的数据。测试按当年的 schema 建库写入，再用最新代码打开逐级升到 v8，逐项比对：条数、每个字段、原图每个字节、新枝来源、嫁接次数回填、套路墙、每日一穗、索引表、uid 唯一且时间对得上；最后导出 .glean 再导进空库，结果一致。以后每加一个 schema 版本就加一份夹具
- **Obsidian 导出适配墓碑**：回收站里的穗和新枝不导出；`glean_id` 写 uid

**性能与内存（InstaBox e2e，1000 穗含 300 张各不相同的原图）**
- 冷启动 196ms（4 倍降速 583ms）；同一台机器交替测 5 轮：v0.20 181 / 533ms，v0.21 185 / 546ms，在误差内。搜索 ≤19.2ms，滚动 60fps
- 导出备份：97.5MB 原图 → 98.0MB 的 .glean，618ms，JS 堆只涨 32.8MB（旧做法光 base64 + JSON 字符串就要 2 倍以上原图大小）
- 新设备导入这份备份：943ms，JS 堆涨 38.3MB，1000 穗 / 300 张图一张不少、sha256 全对
- 数字见 docs/perf/v0.21.0.json

**质量**
- 新增单测：src/__tests__/datafound.test.ts（ULID、SHA-256 / CRC 分块、自动盖章、墓碑与回收站、.glean 结构与哈希、导入三种模式、去重、坏图坏行、旧 JSON、Obsidian）、src/__tests__/migrate.test.ts（v1–v7 迁移回归）
- e2e 新增 datafound()（uid、删除 → 回收站 → 恢复 → 彻底删、导出 .glean 并在 Node 里逐文件核对 sha256、同机再导入新增 0、新设备导入、旧 JSON 导入与再导入、替换进回收站与全部恢复）和 perfBackup()（1000 穗 / 300 图导出与导入的内存）

**没做 / 推迟**
- 0602 的 HLC 混合逻辑时钟：本版只有 updatedAt + deviceId，HLC 和字段级合并（0619）放到同步那一版
- 同组 D1 P0 里成本 S 的 0605（写入失败兜底队列）、0609（备份到指定文件夹）、0622（清空前强制自动导出 + 输入确认）、0624（升级前自动导出原始库）这版没顺手做；0615 / 0618 / 0628 属于同步，等同步版
- 墓碑按 ideas 原文是「90 天且所有设备已同步」再清；现在还没有同步，所以按回收站规则 30 天清

**已知限制**
- .glean 是标准 ZIP（只存储不压缩），超过 4GB 或 65535 个文件会提示导出失败（足够几万张图）
- 网页版导出时由浏览器把各块拼成一个文件再下载，原图块不经过 JS 内存，但浏览器本身仍会占用等量磁盘缓存
- 替换导入不另存一份 .glean 快照，本机被替换掉的东西在回收站里，30 天后自动清
