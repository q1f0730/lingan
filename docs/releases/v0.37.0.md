## 拾穗 · Glean v0.37.0 — 工程底座：大库也快，发版更稳

这一版不加新玩法，专心把底座打牢：大库（几千穗以上）打开穗仓时先只读最新 60 穗（标题照样是真实总数），1 万穗也是一眨眼出卡片；速记回车后新卡片立刻出现，不再等整库重读；大图在详情里先看 1440 宽的「详情档」，点一下换原图；发版流程多了几道闸——e2e 搬进 GitHub Actions 挡在发版前面，Release 先建草稿、产物全部核对完才公开，还有 1 万 / 5 万穗的压力基准和性能回归门。

**下载**：安卓 `Glean_0.37.0_android.apk` · Windows `Glean_0.37.0_x64-setup.exe`（或 `.msi`）· 浏览器扩展 `glean-extension.zip` · Agent 桥 / 命令行 `glean-mcp.mjs` · 校验 `SHA256SUMS.txt`

**升级**：Windows 装着 v0.25 – v0.36 的会自动收到（更新前先自动备份）；安卓 v0.26 起可以在 设置 → 更新 里直接「下载并安装」。数据库不变（仍是 Dexie v12），不用迁移；原图表每行多一个本机派生的「详情档」（不加索引、不进备份和同步），升级后空闲时在后台给旧图补做一次。

**做了哪些（编号见 docs/ideas/ideas.csv）**

大库也快
- **0702 首屏只查最新 60 条**：库超过约 4000 穗时，穗仓打开时按时间索引只取最新 60 穗先画出来，标题的计数用索引直接数（真实总数，不是 60）；全库在首屏画完、手机空闲时再读进来（小库分两段反而多几次查询，实测 1000 穗会慢 15%，所以小库照旧一次读完），类型筛选、穗束、待理 / 缺为什么、回顾、标签云这些要全量的东西那时出现。打开搜索、点「选择」会立刻读全量，不会只搜到 60 条
- **0723 速记回车到卡片出现 ≤100ms**：以前新穗要等数据库把整个穗仓重读一遍才出现（1000 穗时这一步占了大半），现在存好就直接插进列表，整库结果随后到再对齐；e2e 里 1000 穗、5 次中位数断言 ≤100ms
- **0713 图片三档**：缩略图（网格，长边 400）/ 详情档（长边 1440，只给长边 > 1600 或 > 400KB 的大图做）/ 原图。详情页先看详情档，解码快、省内存；**点图换原图**（看截图里的小字）。导出、分享、看图 AI、图中文字识别仍用原图；详情档只在本机，不进备份和同步。旧图在升级后空闲时补一次
- **0703 / 0715 1 万 / 5 万穗压力夹具**：`e2e/stress.mjs` 种 1 万穗（3000 张各不相同的图）和 5 万穗（纯文字），量冷启动（普通 + 4× 降速）、滚动、秒搜、导出；多个版本挂在同一个源、同一会话交替测（数字见下面「性能」）

写入与守门
- **0709 仓储层**：视图和组件里散落的直接写库（新枝星标 / 状态 / 追问 / 结果、花园放入拿出、补为什么、链接补全、讨厌标记……）全部收进 `lib/repo.ts`，「改了这个字段要连带什么」在一处（比如补了为什么，旧向量作废）；单测扫 views / components / App 的源码，再出现 `db.<表>.add / update / modify …` 就失败

发版流水线
- **0705 e2e 进 GitHub Actions**：每次推送跑一遍完整 e2e（性能组仍在固定机器上当门），发版的 verify 也跑，ALL PASS 才往下走
- **0755 e2e 失败存 trace**：哪个用例出错，就把那个浏览器上下文的 Playwright trace（带截图和 DOM 快照）作为附件上传
- **0728 Release 先建草稿**：安装包、签名、latest.json、SHA256SUMS 全部传完核完才公开；所以发布中途老版本的自动更新看不到半成品
- **0729 同步后核对远端**：`ghsync --verify` 拿远端整棵树按 git 内容哈希和本地逐个比，缺的、不同的、远端多出的一目了然
- **0739 一键发版前检查**：`scripts/preflight.sh`（类型检查 / lint / 单测 / 构建 / 体积预算 / 发布说明带编号 / 性能记录 / ideas.csv 换行 / 私钥扫描 / 锁文件）
- **0727 性能回归门**：`scripts/perf-gate.mjs` 读同会话交替测的结果，新版冷启动中位数慢超 10% 且统计显著才拦（一次离群不拦，真变慢拦得住）

顺带
- 文件读写不再打包 `@tauri-apps/plugin-fs` 的 JS（一整套 FileHandle / Resource 类），改成直接调同一套插件命令，省 5.7KB，腾出的地方装下这一版；总资源没超预算（预算不放宽）
- 详情页「1 / 1001」这种四位数的位置不再折行

**性能**：同一台测试机、同一会话交替测，painted 中位数。**1000 穗**（日常规模）：v0.36 198 ms / 4× 降速 597 ms → v0.37 197 / 600 ms，持平（性能回归门 OK）。**1 万穗**（3000 张图）：v0.36 317 / 791 ms → v0.37 219 / 646 ms（快约 30% / 18%），滚动 60fps，秒搜 25 → 23 ms，导出 61.6MB 用 2.0 秒。**5 万穗**（纯文字）：v0.36 647 / 1690 ms → v0.37 211 / 624 ms（快约 3 倍），全库在首屏后约 0.5 秒补齐。速记回车到卡片出现：1000 穗 5 次中位数 11 ms。秒搜 1000 穗 ≤17.8 ms，备份 1000 穗 / 300 图 634 ms。详细数字 docs/perf/v0.37.0.json

**已知问题 / 没有真机验证**
- 文件写入改成直连插件命令后，没在真 Windows 上试过自动备份 / 导出写文件（参数和官方 JS 包逐条对过，e2e 只测网页版）
- 大库升级后**第一次**打开仍按旧办法一次读完（App 要先读一遍才知道库有多大），第二次起才是「先 60 条」
- 首段只有 60 条的那一瞬（通常不到半秒）里，类型筛选和待理 / 缺为什么那几行还没出来，全量到了才出现
- 详情档用 JPEG：透明背景的 PNG 在详情里先显示成白底，点图换原图才是透明的
- 还没做（剩余 P0）：0013 公众号正文快照、0017 链接快照、0015 / 0801 网易云歌单整单拾进、0804 RSS、0104 作品实体、0105 穗间连线、0106 / 0109 向量类（语义搜索 / 母题聚类，下一包）、0415 字体放大 1.3 倍、0805 插件权限、0907 敏感穗上锁
